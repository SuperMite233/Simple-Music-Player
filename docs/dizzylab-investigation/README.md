# Dizzylab 第三方客户端能力调查

初始调查日期：**2026-10-28（Asia/Shanghai）**。目标项目：SMP / Android_MusicPlayer。目标站点：[Dizzylab](https://www.dizzylab.net/)。本目录主体保留初始调查证据；后续代码实现、范围调整和验证结果见 [implementation-status.md](implementation-status.md)。

**后续实施约束：不实现原生付费购买、付费订单创建或支付 SDK。** 购买付费专辑必须引导到 WebView；免费专辑领取和 CDK 兑换在原生界面完成。调查中记录的支付端点仅作为网站行为证据，不属于原生客户端实现清单。

## 结论与阅读入口

**本项目具备扩展成 Dizzylab 第三方客户端的技术基础。** 当前网站存在仍可用的 JSON API，覆盖发现、专辑与社团、搜索、已购、喜欢、关注、动态、购物车查询、播放及单曲下载。网页版另有 Cookie/CSRF、HTML 页面及整包下载流程。建议采用 **JSON API 为主、网页适配为补充、复杂交易与账号操作保留受控网页入口** 的结构。

初始调查时项目采用已购库网页解析，直接继续扩充正则抓取不足以支撑这个目标。实施重点是会话分层、稳定曲目 ID、资源按需解析、试听与下载分离及多来源凭据隔离；当前完成情况见实施记录。

## 证据等级与调查方式

- **V：实时验证**。使用本机 Agent-Browser **0.38.1** 驱动 Microsoft Edge，完成页面浏览、页面 JavaScript 请求观察及针对已发现接口的有限请求。媒体和整包链路另用内存会话做 Range 抽样，每个最终资源只读取 1,024 bytes。
- **S：静态发现**。来自当前网页的表单、链接、内联脚本、`dizzz.js?version=105`，或用户提供 APK 的包内 JavaScript。只能说明客户端如何调用，不能当成服务端已执行成功。
- **I：设计推断**。基于 V/S 给出的实现方案，不代表已实现或官方承诺。
- **U：未知/待验证**。没有用实际结果覆盖的生命周期、写入效果、异常和特殊商品。

已尝试直接复用 Edge 默认配置和 Cookie；Cookie 为 `v20` 格式，复制到独立 Edge 配置后没有恢复登录。未破解或绕过浏览器加密。用户随后授权临时使用账号凭证，本次成功的登录态验证来自 **Agent-Browser 的独立 Edge 测试会话**，不能描述成成功重放了原 Edge Cookie。

网页登录成功后访问个人库页面，发现其内嵌 API Token；另外验证了 APK 的 JSON 登录接口仍返回 Token。Token-only、Cookie-only、游客、无效 Token 均有对照请求。凭证只用于本次测试，没有加入项目配置、脚本或文档；证据里的 Token、CSRF、下载 `k` 和媒体签名均使用占位符。采集过程中曾在网页摘要中混入内嵌 Token/CSRF，已清除并补上脱敏检查。测试浏览器、临时 Edge 配置/Cookie 副本及原始 HAR 已清理并验证不存在。

本次未安装、运行 APK。APK 的 Android REA provider 不支持当前 Windows，改用已有 Android SDK 的 aapt 解码声明、提取明文 React Native bundle，并用 REA 做静态 JavaScript 分析。完整 APK/源码不复制进仓库，身份与哈希见 APK 文档。

## 最影响架构的发现

### 1. Cookie 会话和 API Token 是两种能力

`POST /apis/auth/login/` 接收 JSON `username/password`，返回 `token`。`getmyinfo`、`getmydisc` 等在只带网页 Cookie 时，本次返回 HTTP 200 的 HTML；带有效 Token 时返回 JSON。**有效 Token 且完全不发送 Cookie** 的用户资料与已购请求也已成功。

已登录的 `/u/<uid>/music/` 页面本身会把 Token 写入播放器请求 URL。这提供一条由网页登录衔接 API 的候选路径：在受信站点范围内取得当前页面的 Token，然后用 `getmyinfo` 验证。它是本次页面实现观察，并非稳定公开的 Cookie→Token 交换 API；前端结构变化时应能回退。

### 2. HTTP 200 经常不是成功

缺失/无效 Token、未购单曲下载请求，以及错误方法访问部分路径，均可能收到 `200 text/html` 的“出错了！”页面。客户端必须同时验证 Content-Type、解析结果及业务字段；不能将 HTML 当音频或 JSON，也不能把每个 HTML 错误笼统归为 Token 过期。

### 3. 播放 URL 与下载 URL 的职责不同

详情返回 `tracks[].url`；单曲下载另调 `gettrackdownloadurl`。本次同一已购曲目的播放资源约 5.64 MB，320 下载资源约 14.11 MB，说明不能把播放链接直接当作高品质下载链接。数字仅为单个样本的 HTTP 资源长度，不是全部商品的品质承诺。

`streaming.dizzylab.net` 返回带日期样式片段和签名的路径。应保存 `discid + trackid`，在播放/下载前取得 URL；其真实过期时刻和刷新协议尚未测得。路径出现 `full` 也不能独立作为购买或下载授权依据。

### 4. 网页整包能力显著超过旧 APK

已购页提供 `/albums/download/?d=<discid>&tp=128|MP3|FLAC&k=<signed>&v=1`。三种格式均验证到 `302 → albumsbase.dizzylab.net → 206 application/zip`，具备 Range。没有下载完整 ZIP，也未检查其中曲目/特典内容。

旧 APK UI 仅列出 MP3 128/320；FLAC、特典、下载商品需要网站。若目标是网页版大部分能力，必须独立建立商品、下载格式、文件包与特典模型。

### 5. GET 也可能修改账号数据

网页的支付/加购物车、社团 `?dislike`/`?mailoff`、收件箱 `?m=`、REPO 创建/删除链接，以及 APK 的 `editcart` 等均不能当只读探针。需要按具体动作分类，不能对爬到的 URL 自动遍历。

本次访问“写 REPO”入口后出现一份空白未发表草稿；发现后停止该流程，经用户明确授权删除，并复核编辑器已不存在。**因此不声称调查全程没有服务端副作用。** 没有购买、支付、兑换、发出评论/私信或修改账户设置；其他写接口以静态发现为主。

## 原生客户端实施顺序

1. **P0：契约底座。** 认证状态机、Cookie/Token/CSRF 分离、按域 CookieJar、响应判定、DTO、稳定 ID、日志与配置脱敏。先建立最小请求样本和错误测试。
2. **P1：音乐闭环。** 发现/搜索/社团/专辑/已购、随机听、按需播放解析、授权单曲下载、整包格式选择。沿用本地播放器队列和系统媒体控制。
3. **P2：平台闭环。** 关注动态与远端喜欢、评论/REPO 展示、订单/购物车、消息/设置、兑换和支付网页回退；逐项验证写接口再原生化。
4. **P3：高级与兼容。** 商品特殊类型、特典/ZIP 入库、账号隔离与跨来源混合播放回归、DEFLATE；最后评估运营后台范围。

详细类与目录建议、源码行号、风险和测试见 [integration-plan.md](integration-plan.md)。Subsonic/Navidrome、WebDAV 和本地库继续作为独立来源；Dizzylab 的认证或资源失败不能重置其他来源，也不应接管其 Header、下载协议或导航。

## 明确未完成的调查问题

- Token/签名真实 TTL、服务端撤销、刷新、设备/并发、限流与风控；不通过长期轮询或压力测试推断。
- 所有写操作完整响应和错误码；Toggle 的超时重试可能反向修改状态。
- 真实支付、兑换、付费到账时延、订单状态全集；客户端回调不是购买成功的最终依据。
- 全部商品与预售/实体/下载商品/特典变体；完整 ZIP 内容、单曲 FLAC、断点恢复全过程。
- 非空 REPO/空购物车之外的数据、消息发送/删除、账号修改、游戏/上传后台。
- 网站存在接口不等于有稳定公开 API 或第三方接入承诺；公开客户端发布前需核实平台接入与支付使用条件。

## 验证与复现约束

复现时使用新的临时浏览器会话，先观察网页，再对已确定无业务写入的端点做小样本请求。所有样本以字段结构为主；个人邮箱、用户名值、Cookie、Token、CSRF、签名、订单和消息标识不进入样例。不要把当前个人库中的商品清单作为固定测试数据。

初始端点调查阶段没有 Android 代码修改，未运行 Gradle 构建或新增应用单测。当时的文档交付检查包括 JSON 可解析、文档链接与源码位置、脱敏扫描、证据索引哈希和临时会话清理。后续 Android 实现的构建、单测与模拟器结果见 [实施记录](implementation-status.md)。
